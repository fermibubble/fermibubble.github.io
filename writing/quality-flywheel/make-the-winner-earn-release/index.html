Make the Winner Earn Its Release

Selection finds a promising candidate. Independent evidence earns the release.

The richer incident snapshot looks promising. The team tries several variations and chooses the one with the highest development score. It fixes the original credential incident. Should it replace the current Atlas?

Not yet. The team selected this version because it looked good on cases it had already inspected. Some of that advantage may come from learning the particular cases, and some may come from favorable runs. The selection process is part of the evidence.

Compare changes on the same work

Run the current version and the candidate on the same incident snapshots, with comparable tool behavior and budgets. Record disagreements, not just their separate totals. The interesting cases are the ones that improved and the ones that regressed.

In this example, accuracy rises from 80% to 86%. The change repairs fourteen incidents and breaks eight. “Six points better” is true, but it is an incomplete release argument. If the eight regressions include rare, expensive actions, the average may conceal a bad trade.

Read the disagreements. Did the candidate interpret a carrier's 429 response as an authentication problem? Did the new summary omit evidence that the old version used? Did the evaluator mislabel a reasonable temporary mitigation as a final diagnosis? The comparison is a way to learn, not merely a gate to clear.

One hundred incidents also do not settle the size of the gain. Cases differ in difficulty, repeated attempts vary, and several cases may come from the same underlying outage. Adding Error Bars to Evals explains why uncertainty and experimental design belong in evaluation. Repeated trajectories from one incident should not masquerade as independent evidence from many incidents.

Give discovery and confirmation different jobs

Development cases are for investigation. Inspect them, argue about them, and use their failures to generate candidates. Confirmation cases answer a different question: does the selected change work on incidents it was not tailored to?

For Atlas, that means unfamiliar credential rotations, genuine capacity incidents, throttling, and healthy controls sampled to reflect the intended work. Keep the confirmation cases out of the optimizer's feedback. If their failures are used to revise the candidate, those cases have become development material; the next confirmation needs independent evidence.

Research on adaptive data analysis explains why reusing data to choose the next hypothesis can undermine ordinary statistical guarantees. There is no magic in the word “holdout.” Repeatedly checking a private score and changing the system in response still lets information about that set guide the search. The more candidates a team tries, the more care it owes to how the winner was chosen.

Match the test to the responsibility

Atlas currently advises an engineer. The engineer can reject a bad recommendation. Giving Atlas permission to act unattended changes the quality requirement even if its model and prompt stay identical.

If each attempt independently succeeds with probability 0.8, five attempts have a 99.97% chance of containing at least one success, but only a 32.77% chance of all succeeding. The first situation can help someone who can recognize and select a good answer. The second resembles a system expected to complete a sequence of jobs reliably. Real attempts can be correlated; the distinction still matters.

τ-bench brings consistency across trials into agent evaluation. A more recent preprint, Locating Hidden Failures Makes Long-Horizon Agents More Reliable, examines errors inside trajectories that an endpoint score can miss. Both point back to Atlas's opening incident: the final state can look good while the process contains a lesson we should not repeat.

Atlas's review finds that the candidate sometimes jumps from a growing queue to a credential repair, even when the snapshot reports throttling. The team keeps the richer snapshot but removes this shortcut from the procedure. On fresh incidents, the revised version distinguishes the credential, capacity, and quota cases; repeated trials and human review support a limited release. It stays advisory, with an engineer approving each action.

A release decision should therefore include diagnostic quality, inappropriate actions, latency, and recurrence—not only whether the queue eventually drained. A staged rollout then tests what replay cannot: the changing carrier, traffic, and operating conditions. Keep a rollback path and inspect whether the predicted improvement appears in use.

Offline comparison and live observation complete each other. The comparison helps isolate a change. Real use reveals whether the change mattered in the world where Atlas has to work.
