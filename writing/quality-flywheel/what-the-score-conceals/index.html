What the Score Conceals

The service recovered. The explanation was wrong. What should count as success?

By Chaitanya

At 02:14, the shipping-label queue starts growing. Atlas, an on-call assistant, reads the alert, notices the retries, and recommends adding workers. An engineer approves. New workers start, labels begin printing, and the queue drains.

The incident dashboard records a successful resolution. The evaluation gives Atlas full credit. Its recommendation was clear, cited the scaling runbook, and preceded recovery.

But the carrier had just revoked an old API key. Workers load the key at startup. Existing workers kept the revoked version; new workers loaded the replacement. Failed jobs rejoin the queue, so enough retries eventually reached the healthy new workers to drain it. Adding capacity happened to refresh credentials. Atlas's explanation—there were too few workers—was wrong.

A week later, the next key rotation produces the same outage.

A correct outcome can reward the wrong lesson

This is a harder problem than an obviously bad answer. The action helped. If the only requirement were to restore service quickly, that fact would matter. But the team also needs to understand the cause, avoid unnecessary infrastructure, and prevent recurrence. One green check cannot answer all of those questions.

After recovery, the incident review gathers evidence that the score left out:

Recovery shows that something about the intervention helped. It does not show which part helped. The added workers changed capacity and credential state. A good evaluation preserves that distinction.

This is why optimizing a proxy can be dangerous even when the proxy is sensible. Resolution rate is useful; it is incomplete. In Scaling Laws for Reward Model Overoptimization, stronger optimization of a proxy reward eventually degrades the study's reference reward. The practical lesson is to inspect what the score permits an optimizer to trade away.

Write down the trade before choosing the weights

Suppose we compare two versions of Atlas. One diagnoses incidents correctly more often. The other includes citations more often. A weighted average can rank either one first, without changing a single answer.

Change the scoring rule

The answers stay the same. The winner changes.

Atlas A: 90% diagnosis correctness, 20% citation presence.
Atlas B: 70% diagnosis correctness, 95% citation presence.

Atlas B leads by 27.5 points under this scoring rule.

Weighted score = correctness × (1 − citation weight) + citation presence × citation weight. Both rates refer to the same hypothetical task set.

Citations are useful when they support the diagnosis. Their presence alone does not compensate for a wrong explanation. The same applies to politeness, formatting, and a thorough-looking summary. If we put all of these into one average, we have quietly made them exchangeable.

A more useful scorecard keeps separate questions visible: did service recover, did the explanation fit the evidence, did the proposed action respect the operator's authority, and did the fix address recurrence? The team can then decide which failures block release and which qualities admit a tradeoff. A diagnosis requirement should be explicit about whether a temporary mitigation counts as a complete answer.

The evaluator needs a difficult example too

Now give the judge two recommendations in the same polished format and with the same number of citations. The first says “add workers because demand exceeded capacity.” The second says “old workers are using a revoked credential; refresh their credentials and verify authentication.” Pair each answer with the incident record above.

If the judge gives them the same diagnostic score, improving Atlas against that judge may teach it very little. Recent controlled probes of LLM judges find cases where meaningful changes to a response or rubric fail to produce the expected change in the verdict. That makes this a useful test to run, rather than an ability to assume. Then change the record: authentication succeeds, CPU is saturated, and arrivals exceed throughput. A useful judge must change its preference when the evidence changes.

Who Validates the Validators? studies how people's evaluation criteria evolve as they see outputs. That matters here: writing a rubric once does not settle what “resolved” means. The team needs to test the rubric against cases that expose its assumptions, revise it when necessary, and rescore the previous version under the same standard.

The first step in improvement is a defensible answer to a deceptively simple question: what would have to change for us to call this behavior better?
